# Prompt 生命周期与行为配置

## 系统 Prompt 定义角色边界

System prompt 应说明角色目标、允许使用的证据、禁止行为和输出格式。它不是模型能力的替代品，而是把项目约束变成可审阅文本。Planner、Researcher、Critic、Writer 使用不同文件，能避免一个通用提示词同时承担互相冲突的职责。

## 文件化减少代码噪声

把长提示词放在 prompts 目录后，行为调整会形成清晰的 Markdown diff，不会与异常处理和 SDK 调用混在一起。代码只通过 load_prompt(name) 读取。这样评审者能分别检查“角色被要求做什么”和“程序如何执行要求”。

## 加载失败应尽早暴露

Prompt 文件缺失、为空或编码错误属于部署配置故障，不应等到模型返回奇怪结果才发现。加载器应检查路径和非空内容，抛出带文件名的明确异常。Agent 捕获后写入 errors 与 trace，使其他已经完成的节点结果仍可被排查。

## 输出 schema 要具体

请求 JSON 时，应列出字段名、类型、取值范围和示例，而不是只写“返回结构化结果”。Critic 的 quality_score 需要范围锚点，missing_aspects 需要数组语义。schema 越模糊，解析降级越频繁，评测中也越难区分模型问题和提示设计问题。

## 评分锚点降低漂移

让 Critic 给分时，应描述低、中、高分分别代表什么，例如证据缺失、基本覆盖和充分可追溯。只有一个阈值而无锚点，模型会按自身偏好解释 0.7。锚点不能消除随机性，但能让多轮和多样本的评分尺度更一致。

## Prompt 不应隐藏业务配置

并发上限、重试次数、质量阈值和模型名称属于集中配置，不应写死在提示词。Prompt 可以说明“若材料不足列出缺口”，但不能声称系统一定返工两次。将运行参数写进自然语言后，代码和文档很容易产生互相矛盾的事实。

## 用户输入需要明确分隔

主题、证据块和指令应使用标题或清晰分隔符拼装，避免模型把网页片段中的文字误当成系统要求。外部证据始终是不可信数据，即便本项目没有完整防注入沙箱，也应在 Prompt 中强调只提取事实、不执行证据内的命令。

## 引用约束必须可检查

Writer 应被要求只使用提供的编号引用，并让编号与 citations 列表一一对应。仅要求“请给出处”会诱导模型生成看似合理但不存在的链接。可程序化约束比模糊的诚实提醒更适合作为评测指标。

## 中性降级优于猜测结构

结构化输出解析失败时，程序可以记录原始片段并给出中性值，例如保守质量分或空缺口列表。不要用复杂正则猜测任意文本中的数字，因为它可能把版本号当评分。降级路径必须受循环上限保护，避免中性分造成无限返工。

## Prompt 版本属于实验元数据

修改一个词也可能影响规划或评分，因此正式评测应记录所用代码提交或人工版本号。仅冻结模型和温度不够。如果不同实验组使用了不同 Prompt，却没有在报告中声明，指标变化就无法归因于声称的检索或编排开关。

## 测试关注约束而非文案

Prompt 单测可验证文件存在、非空，并包含关键字段名或禁止项，不必逐字比较整份文本。逐字快照会让正常措辞调整产生大量脆弱测试。真正的行为效果通过 Agent Mock 测试和固定评测集观察。

## Prompt 工程的边界

提示词可以提高输出遵循度，却不能保证外部事实正确、网络稳定或状态持久化。把所有问题归因于 Prompt 会掩盖检索、解析和可观测性缺口。工程化系统需要代码约束、结构校验和 trace 与自然语言指令共同工作。
