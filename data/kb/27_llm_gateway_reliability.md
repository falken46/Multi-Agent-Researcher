# LLM 网关、重试与成本收口

## 唯一入口保证统计完整

所有 Agent 和 LLM reranker 都经由 core.llm 的 chat 或 achat 调用模型。网关统一获得 node 与 trace_id，因此每次成功、失败和重试都能归属到正确节点。如果某个角色直接构造 SDK 客户端，它消耗的 token、成本和延迟就会从汇总中消失。

## 同步与异步接口共享语义

chat 面向同步节点，achat 面向异步 Researcher，但两者应使用同一配置、重试策略、响应结构和 trace schema。只有执行方式不同，不能让异步入口少记成本或采用另一套异常类型。统一的 LLMResult 也让节点测试更容易替换返回值。

## 超时必须显式配置

模型调用不能依赖 SDK 的无限或隐式默认等待。LLM_TIMEOUT 定义单次请求可接受的上界，并由 Pydantic 校验为正数。外层研究任务还可能包含 embedding 与搜索，因此它的总超时应大于单次模型超时，而不是简单使用同一个数字。

## 指数退避处理瞬时失败

网络抖动、临时限流和服务端错误通常可以重试，退避间隔随尝试次数增加能避免立即再次冲击服务。认证失败、非法参数等永久错误不应盲目重试。每次尝试都要记录 attempt 和失败原因，最终异常再转换成明确的 LLMError。

## 重试次数与调用次数不同

一次业务上的模型调用可能包含多次网络尝试。成本汇总应依据服务端实际返回的成功 usage，错误事件则记录失败尝试。评测报告要说明“LLM calls”统计的是成功响应还是所有尝试，不能把两个口径混为一个数字。

## Token 取服务端 usage

prompt_tokens 和 completion_tokens 应优先读取模型响应 usage，而不是用字符串长度推算。不同分词器对中文、代码和标点差异很大。若服务商没有返回 usage，可以记录缺失或使用明确标注的估算，但不能把估算伪装成真实计费数据。

## 成本换算与调用解耦

core.costs 根据模型名称、输入输出 token 和版本化价格表计算成本，LLM 网关只负责传递计量结果。未知模型可以返回零成本并发出警告，避免任务因价格表落后而失败，但报告必须说明该样本成本不完整。

## JSON mode 仍需解析校验

请求 json_mode 可以提高结构遵循度，却不保证字段齐全或值域正确。节点仍要 json.loads、检查类型并执行业务范围裁剪。把供应商的 JSON 开关当成 schema validator，会让少见错误直接污染 ResearchState。

## 错误信息避免泄露密钥

网关日志可以记录模型、状态码、尝试次数和截断消息，但不能打印 Authorization header 或完整配置对象。SecretStr 只保护默认显示，手动调用 get_secret_value 后仍需谨慎。提交 trace 前也要确认 payload 不包含用户密钥。

## node 和 trace_id 不可省略

node 用于按角色聚合成本，trace_id 把同一次研究任务的多次调用串起来。自动生成缺失 trace_id 虽能让单次调用成功，却会割裂全链路数据，因此业务调用方应在任务入口创建并持续传递同一个标识。

## Mock 应停在网关边界

Agent 单测替换 core.llm.chat 或 achat，即可固定模型输出并验证消息结构。没有必要 Mock SDK 内部的 HTTP 层，那会使测试耦合供应商实现。网关自身的测试再覆盖重试、usage 解析、trace 和异常转换。

## 更换模型不应修改 Agent

模型名、Base URL 和 API Key 由 Settings 提供。切换兼容服务时，Agent 代码和 Prompt 加载方式保持不变。若迁移要求修改每个节点，说明调用边界仍然泄漏了 SDK 或供应商细节。
