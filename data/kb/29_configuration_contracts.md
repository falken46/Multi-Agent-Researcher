# 集中配置、校验与实验快照

## Settings 是唯一声明入口

core.config 用 Pydantic Settings 集中声明模型、检索、编排、trace 和前端配置。业务模块通过 get_settings 读取，不直接调用 os.getenv。统一入口使类型、默认值和文档位置清晰，也方便测试通过构造 Settings 隔离环境。

## 类型转换发生在边界

环境变量本质上是字符串，Pydantic 负责转换为 int、float、bool、Path 或 Literal。业务代码因此不需要重复解析。非法值应在启动或显式加载配置时失败，而不是运行到某个深层节点才出现难以理解的类型错误。

## 单字段约束防止无效值

超时必须大于零，重试次数不能为负，质量阈值应限制在零到一之间。Field 的 gt、ge 和 le 把这些规则放在声明附近。靠每个调用点自行判断会产生不一致，有的路径可能接受零并立刻超时，有的路径又静默使用默认值。

## 跨字段校验表达组合规则

chunk_overlap 单独看可以是非负整数，但还必须小于 chunk_size。model_validator 适合这类涉及多个字段的约束。若只在 splitter 运行时校验，错误配置可能已经通过启动检查，并在建库长流程中途才失败。

## Literal 限制后端枚举

embedding_backend、rerank_backend 和 search_provider 使用 Literal，避免拼写错误悄悄选择意外分支。新增后端时要同时扩展类型、工厂函数、环境示例和技术栈说明，不能只让某段业务代码认识新字符串。

## SecretStr 保护默认展示

API Key 使用 SecretStr，可以减少配置对象被日志打印时直接泄露的风险。真正调用外部服务时才取出原始值，并检查非空及编码。SecretStr 不是完整密钥管理系统，异常和自定义日志仍必须避免拼接秘密。

## lru_cache 与测试隔离

get_settings 使用进程内缓存，避免每个节点重复读取 .env。测试修改环境变量后必须 clear_settings_cache，否则后一个用例可能继续使用旧配置。缓存提高便利性，也意味着运行中修改 .env 不会自动热更新。

## 路径配置保持相对可移植

知识库、Chroma、BM25、checkpoint 和 trace 默认使用项目相对路径，便于本地和容器挂载。写入前由具体模块创建必要目录。不要把开发机绝对路径写进配置默认值或报告，否则仓库在其他系统上无法复现。

## 新增配置同步三处

代码新增字段时，应同步 core/config.py、.env.example 和 TECH_STACK.md。配置类告诉程序如何读取，环境示例告诉使用者如何设置，技术文档解释为什么存在。漏掉任意一处都会产生文档漂移或不可发现功能。

## 实验组必须保存快照

评测结果应记录 retrieval_top_k、RRF k、rerank 后端、并发上限、质量阈值、模型、数据集版本和价格版本等完整字段。只记录组名不足以复现，因为默认值以后可能变化。报告生成器应拒绝聚合版本或关键配置字段不一致的运行。

## 覆盖配置不应污染全局

CLI 可以用 model_copy 为一次建库覆盖 embedding 后端，测试也可以显式构造 Settings。临时需求不应改写 .env 或全局缓存后忘记恢复。配置对象尽量按不可变快照传递，能降低并发任务之间互相污染的风险。

## 默认值不等于最佳值

默认并发、阈值和 top_k 只是可工作的起点，必须用真实任务数据校准。尤其不同排序阶段的分数量纲可能不同，同一个 KB_SCORE_THRESHOLD 不能未经验证就套在 RRF 分数和 cross-encoder 分数上。
