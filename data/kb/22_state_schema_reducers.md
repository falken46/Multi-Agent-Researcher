# 共享状态、局部更新与合并语义

## TypedDict 是角色协议

ResearchState 用 TypedDict 描述 topic、sub_questions、research_results、citations 和 errors 等字段。它首先是 Agent 之间的静态协议，而不是运行时数据库。Planner 写入规划，Researcher 消费子问题并补充证据，Critic 读取材料给出评价，Writer 最后消费已经约定的字段。

## 字段所有权减少耦合

为每个字段指定主要生产者和消费者，可以避免两个节点用不同含义写同一个键。例如 quality_score 应由 Critic 产生，Writer 只能读取；fallback_queries 由 Researcher 累积，Planner 不应重置。字段所有权比单纯添加类型提示更能约束多人协作和后续扩展。

## 局部更新不是整态替换

LangGraph 节点返回的字典表示本节点产生的更新。只返回改变的字段，可以降低误删 checkpoint 中其他值的风险。如果节点总是复制整份状态，新增字段后旧节点可能用缺省值覆盖新数据，形成只在恢复路径出现的隐蔽兼容问题。

## Reducer 解决并行写冲突

多个并行节点同时更新同一字段时，需要清晰的 reducer 决定合并方式。列表可以拼接，计数可以求和，字典可以按键合并，但每种语义都要显式选择。没有 reducer 的并发写入可能以后完成者覆盖先完成者，使成功结果随调度时序丢失。

## 可变容器要复制后修改

从 state 取出的 list 或 dict 不应直接原地修改后复用。更安全的做法是先创建副本，在副本上追加，再作为节点更新返回。原地修改可能绕过框架的变更检测，也会让测试中的输入 fixture 被污染，造成多个用例之间相互影响。

## 可选字段与初始状态

TypedDict 的静态声明不等于运行时一定存在所有键，尤其是旧 checkpoint 或最小测试输入。节点读取非核心字段时通常使用明确默认值，例如 state.get("errors", [])。但 topic 这类必需输入应尽早验证，不能把缺失悄悄转换成看似成功的空报告。

## Schema 演进需要兼容策略

加入新字段时，要考虑已有 checkpoint 中没有该字段的情况。可选读取和中性默认值可以支持向前迁移；删除或改名则需要版本字段或迁移脚本。直接假设所有持久化状态都来自最新代码，会让升级后的恢复请求在生产中集中失败。

## 状态不等于长期指标仓库

ResearchState 保存当前任务继续执行所需的数据，JSONL trace 保存长期审计事件。把每次 token、耗时明细都不断塞入状态会膨胀 checkpoint，也让恢复负担越来越重。状态可保存汇总展示值，但评测指标的事实来源仍应是 trace 或评测原始产物。

## 序列化边界要简单

Checkpoint 通常要求状态可序列化，因此字段应优先使用字符串、数字、列表、字典等稳定结构。打开的文件、客户端连接、锁和协程对象不应进入 ResearchState。外部资源在节点执行时创建并及时关闭，只把必要的标识和结果写回状态。

## 错误列表也需要结构意识

简单字符串适合早期展示，但随着评测增加，错误最好能区分节点、类型、消息和是否致命。即便暂时仍使用字符串，也应保持固定前缀并把完整结构写入 trace。不要从自由文本日志用正则反推失败率，那会使指标依赖文案。

## 状态契约的单元测试

测试应验证每个节点只写预期字段、不会修改输入容器，并能处理缺少可选键的最小状态。图测试还需验证一次循环后 quality_history 和 revision_count 的演进。单纯断言最终报告非空，无法发现中间字段被错误覆盖的问题。

## 显式状态带来的面试价值

清晰 schema 能回答“多个 Agent 如何共享上下文”这一高频问题：不是把全局变量传来传去，而是通过有类型的状态协议和图边控制读写。进一步说明 reducer、持久化兼容和字段所有权，才能体现工程化编排而非仅仅调用框架 API。
