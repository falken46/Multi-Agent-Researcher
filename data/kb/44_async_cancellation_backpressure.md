# asyncio 取消、超时、Semaphore 与背压

## 并发收益来自重叠等待

Researcher 的多个子问题主要等待本地 embedding、搜索网络和 LLM 响应。串行执行会把这些等待时间相加，`asyncio.gather` 可以让独立任务同时等待，因此降低墙钟耗时。它不会自动减少每个调用的 token，也不会让 CPU 密集型 rerank 获得线性加速。

## Semaphore 限制在途任务

直接为几十个子问题创建任务会同时冲击模型和搜索服务。`asyncio.Semaphore` 把“允许并发”与“无限并发”区分开：任务可以全部创建，但只有获得许可的少数任务进入实际研究链。上限应根据服务限流、连接数和成本校准，而不是越大越好。

## 背压不是简单 sleep

固定 sleep 只能降低平均请求频率，无法感知当前积压。Semaphore 通过许可数量表达容量，调用完成后立即释放；队列增长时新任务自然等待。若外部 API 还限制每秒请求数，可在 Semaphore 外再增加速率限制，但当前个人项目先控制最大在途数已经覆盖主要风险。

## 超时应包住完整子任务

只给 LLM SDK 设置超时，无法限制前面的 KB、Web 搜索和线程切换。Researcher 使用 `asyncio.wait_for` 包住单个子问题的整条链路，预算包含 LLM timeout、embedding timeout 和额外搜索余量。这样某个服务卡住不会无限占用一个 Semaphore 许可。

## `to_thread` 解决阻塞函数接入

现有 kb_search 和 web_search 是同步函数，直接在 async 节点调用会阻塞事件循环，使其他协程无法推进。`asyncio.to_thread` 把同步 IO 放到工作线程，事件循环继续处理其他子问题和 SSE。它不是把所有代码线程化，LLM 的 async 接口仍直接 await。

## 线程取消具有边界

取消等待 `to_thread` 的协程，并不保证底层线程中的同步函数立即停止。网络库可能直到自己的超时才返回。外层 wait_for 能让主流程不再等待，但线程资源仍可能短暂占用。因此同步工具本身也要设置合理 timeout，不能只依赖 async 外壳。

## gather 的异常策略决定隔离程度

默认 gather 遇到一个异常会把异常抛给调用方，其他任务的处理容易被中断。`return_exceptions=True` 将每个结果或异常放在对应位置，Researcher 可以逐项保留成功摘要并把失败写入 errors。这适合“部分结果也有价值”的研究任务，但调用方必须显式识别 BaseException，不能把它当正常结果。

## 取消传播要区分用户取消与局部超时

单个子问题超时可以记录错误并继续其他任务；用户主动取消整个研究任务时，通常应取消所有未完成子任务。若所有 CancelledError 都被当普通异常吞掉，后端会继续花费 API 成本。异常处理需要保留任务级取消的传播语义，同时隔离局部业务错误。

## 并发完成顺序不应改变输出顺序

速度快的子问题可能先完成，但 `gather` 返回结果顺序与输入 awaitable 顺序一致。项目按原目标列表 zip 结果，保证 research_results 和 citation 的组装顺序稳定。若改用 `as_completed`，可以更早推送细粒度进度，但需要额外保存任务到原问题的映射。

## 超时任务也要释放 Semaphore

使用 `async with semaphore` 能在正常返回、异常或取消时执行退出逻辑并释放许可。手动 acquire 后忘记在 finally 中 release，会导致后续任务永久等待，看起来像外部服务超时。上下文管理器是并发资源安全的基础，不只是语法简化。

## 并行基准必须固定工作量

比较 concurrency=1 与 3 时，子问题数量、文本、证据、模型和 Critic 开关必须相同。否则耗时差可能来自不同 Planner 输出或不同联网结果。微基准应重点报告 Researcher 节点墙钟耗时，并检查两组 LLM 调用数和 token 大致一致。

## P95 与少量样本

并发性能容易受网络抖动影响，单轮五个主题只能给方向性结论。若要把百分比写进简历，至少做多轮配对测量并报告中位数或 P95 边界。样本量仍小，应称为受控微基准，不宣称生产环境普遍加速。
