# Checkpoint 恢复、幂等键与重复执行边界

## Checkpoint 保存图状态和执行位置

LangGraph Checkpointer 的核心用途是让中断任务从最近持久化位置继续。它保存 ResearchState、节点进度和框架需要的版本信息，不负责统计 token 或生成评测指标。JSONL trace 记录发生过的事件，两者虽然都持久化，却分别服务恢复与审计，不能互相替代。

## thread_id 与 trace_id 生命周期不同

`thread_id` 标识可以恢复的任务线程，恢复请求必须复用它；`trace_id` 标识一次实际执行尝试，新任务和新的恢复尝试可以产生独立 trace。若把两者混用，一个长生命周期线程的多次执行会写进同一指标文件，或者每次恢复都找不到原 checkpoint。

## 新任务与恢复输入不同

新任务需要完整初始 ResearchState，包括 topic、计数器、引用容器和 trace_id。恢复时不应再次提交相同初始状态，否则框架可能把它解释为新的状态更新并重跑已完成节点。正确做法是先按 thread_id 读取快照、校验 topic，再以 `None` 输入继续剩余执行。

## topic 校验防止串任务

客户端可能错误复用旧 thread_id 提交新主题。如果后端只看 thread_id 并直接恢复，用户会收到另一个任务的状态。恢复入口应比较请求 topic 与 checkpoint 中 topic，发现不一致就明确拒绝。新主题必须生成新 thread_id，只有恢复同一任务才复用。

## durability 决定丢失窗口

同步持久化意味着节点继续执行前先把 checkpoint 写盘，故障后最多重跑当前未提交步骤；异步或退出时批量写入性能更高，但进程崩溃可能丢失更多进度。演示项目任务数量小、节点调用昂贵，选择更强 durability 能减少重复付费调用，代价是每个节点多一次本地 IO。

## Checkpointer 生命周期必须覆盖图执行

`AsyncSqliteSaver.from_conn_string` 返回异步上下文资源。若在 `build_graph()` 后立即退出上下文，再拿已编译图执行，底层数据库连接已经关闭。后端流式函数需要在整个 `astream()` 生命周期内持有 saver，直到最终事件和 checkpoint 都完成后再释放。

## SQLite 适合单机而非共享集群

SQLite 提供简单事务、无需独立服务，适合个人项目和单实例演示。多进程或多机器共享时会遇到文件锁、网络文件系统语义和连接管理问题。生产集群通常改用官方支持的共享数据库 checkpointer，但不应为了展示扩展性在当前项目提前引入运维依赖。

## 恢复不保证外部副作用只发生一次

Checkpoint 可以避免框架忘记状态，却无法回滚已经发送的 HTTP 请求。节点在外部调用成功后、checkpoint 写入前崩溃，恢复时可能再次调用。对于写操作需要幂等键或去重表；本项目多数工具是只读检索，重复调用主要增加成本和延迟，但评测 raw 追加仍需要稳定任务键防止重复计数。

## 任务级幂等键与 chunk_id 不同

chunk_id 标识知识库切片，不能用来判断某个评测样本是否已经完成。批量 runner 应使用样本 ID、实验组和轮次组成运行键，启动时读取已有 raw JSONL，已完成键直接跳过。这样中途停止后可以续跑，而不会把同一观测重复写入均值。

## Trace 在恢复场景中的处理

可以让每次恢复使用新的 trace_id，并在事件中记录同一个 thread_id 和父 trace；也可以沿用原 trace_id 形成一条连续链。前者更容易区分每次尝试成本，后者更容易阅读完整时间线。无论选择哪种，评测口径必须明确，不能把失败尝试 token 悄悄排除又声称端到端成本。

## 恢复测试要真的关闭连接

只在同一个内存对象上中断后继续，不能证明持久化有效。高价值测试应写入临时 SQLite，结束第一个 saver 上下文，重新创建连接和图，再用同一 thread_id 恢复。这样才能覆盖文件落盘、连接生命周期和状态序列化，而不是只验证内存缓存。

## Checkpoint 不是缓存

缓存按输入复用计算结果，Checkpoint 保存某次流程的中间状态。新任务即使 topic 相同，也不应自动读取旧 checkpoint，因为用户可能希望使用更新语料或模型重新研究。Web query 缓存则可以在受控评测中复用相同原始搜索结果，两者的命中条件和失效策略完全不同。
