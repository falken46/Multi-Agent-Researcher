# MCP 工具协议与核心能力复用

## MCP 是协议适配层

Model Context Protocol Server 把 deep_research 和 kb_search 等已有能力注册为外部工具，负责参数 schema、描述、传输和错误映射。它不重新实现 Planner、Researcher 或检索算法。协议层越薄，Web 前端与 MCP 客户端越容易共享同一事实和行为。

## 工具描述面向模型阅读

名称应稳定、动词语义明确，描述说明何时调用、输入限制和返回内容。参数 schema 给出类型、必填项和合理边界。含糊描述会让客户端模型误选工具，即使底层函数完全正确也无法得到可靠使用效果。

## deep_research 与 kb_search

deep_research 适合需要规划、多来源检索、Critic 和报告生成的长任务；kb_search 适合直接查询本地知识切片。两个工具不能只因都“搜索”就合并，否则简单查询也会承担完整 Agent 成本，复杂研究又失去明确入口。

## 核心图保持单一实现

MCP handler 应调用现有 graph 或服务函数，不复制一套 Agent 调度。复制会导致 Web 端有 Critic 和 checkpoint，而 MCP 端仍停留在线性流程。功能修复必须在核心层生效，协议适配只转换输入输出。

## 工具函数仍遵守边界

kb_search MCP 工具可以复用 tools/kb_search.py，但不能直接从 Agent 文件互调节点。MCP 是外部调用入口，不是新的编排框架。内部多 Agent 协作仍由 LangGraph StateGraph 管理，保持项目的核心技术定位。

## 参数校验早于执行

空主题、非法 thread_id 和超出限制的 top_n 应在协议或服务边界返回明确错误，避免进入昂贵模型调用。校验错误属于客户端输入问题，不应计为 Agent 质量失败。真实工具 schema 和 Python 校验必须保持一致。

## 长任务的返回策略

deep_research 可能运行较久，MCP handler 需要考虑客户端超时、进度通知或异步任务标识。简单地阻塞直到完整报告在本地 Demo 可能可用，但文档应说明限制。不要宣称协议自动提供 checkpoint 恢复，恢复仍依赖核心图设计。

## 错误转换保留语义

内部异常应转换为工具可理解的错误结果，同时保留 trace_id 供排查。不能把堆栈和密钥直接返回给外部客户端，也不能把所有异常吞成空字符串。输入错误、暂时服务故障和部分成功需要不同表达。

## 权限不由描述文本保证

工具描述写“只读”不能替代实际权限控制。暴露本地搜索风险较低，未来增加写文件或发消息工具时需要身份认证、授权范围和审计。MCP 负责标准化交互，不会自动解决业务侧安全策略。

## 多客户端兼容性

同一 MCP Server 可被支持该协议的开发工具或桌面客户端发现，但不同客户端对超时、显示和扩展能力的支持可能不同。验收至少需要一个真实客户端成功列出并调用工具，单元测试只证明 server handler 的代码路径。

## 协议测试与核心测试分层

MCP 单测验证工具注册、参数 schema、错误映射和对核心函数的调用；图与 RAG 的行为继续由原有测试覆盖。这样协议升级不会要求重跑真实模型，核心算法变化也无需复制 MCP 专属用例。

## 与 SSE 的职责区别

SSE 是 Web API 向浏览器持续推送当前任务进度的传输方式，MCP 是让模型客户端发现并调用工具的协议。二者都位于系统边界，却解决不同问题。可以让 MCP 工具内部复用研究图，但不能把 SSE 事件名称直接当作 MCP 工具 schema。
